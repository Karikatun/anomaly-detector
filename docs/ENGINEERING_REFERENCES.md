# Проверенные инженерные материалы Martin Fowler

Этот реестр содержит полностью изученные материалы с сайта Martin Fowler,
которые применимы к текущей архитектуре Anomaly Detector. Это не обязательный
набор паттернов: материал используется только при наличии указанной задачи и с
учётом ограничений проекта.

Дата последней проверки материалов: **1 августа 2026 года**.

## Базовые материалы

| Материал | Применение в проекте | Ограничение |
|---|---|---|
| [Monolith First](https://martinfowler.com/bliki/MonolithFirst.html) | Сохранять backend модульным монолитом, пока реальные требования к независимому развёртыванию, масштабированию или владению командами не оправдают разделение. Уточнять границы модулей по наблюдаемым изменениям домена. | Монолит не оправдывает нарушение границ. Публичные API модулей, направление зависимостей и владение данными всё равно должны быть явными. |
| [Bounded Context](https://martinfowler.com/bliki/BoundedContext.html) | Определять продуктовые контексты по единому языку и модели: например, различать Auth, Room и Tender, а интеграцию проводить через явные публичные контракты. | Bounded Context не обязан становиться отдельным сервисом, пакетом или полным набором DDD-слоёв. |
| [Presentation Domain Data Layering](https://martinfowler.com/bliki/PresentationDomainDataLayering.html) | Разделять транспорт/UI, бизнес-правила и доступ к данным внутри продуктового контекста. Это поддерживает текущие backend-слои `transport`, `application`, опциональный `domain`, `infrastructure` и клиентское разделение route/feature/platform. | Технические слои не становятся верхнеуровневыми продуктовыми модулями или границами команд. Простое поле всё ещё может потребовать согласованного изменения нескольких слоёв. |
| [Refactoring Module Dependencies](https://martinfowler.com/articles/refactoring-dependencies.html) | Отделять создание зависимостей от их использования в composition root; передавать контекстам узкие порты и функции; постепенно устранять скрытые глобальные зависимости. | Не требует DI-контейнера или Service Locator. Для текущего TypeScript-кода явных фабрик, замыканий и параметров достаточно, пока более тяжёлый механизм не решает наблюдаемую проблему. |
| [Yagni](https://martinfowler.com/bliki/Yagni.html) | Не добавлять микросервисы, generic repositories, пустые DDD-слои, очереди, флаги и точки расширения для предположительных будущих требований. Добавлять минимальную возможность тогда, когда возникла реальная задача. | YAGNI не оправдывает отказ от рефакторинга, тестов, безопасности и других практик, которые сохраняют код изменяемым. |
| [Optimistic Offline Lock](https://martinfowler.com/eaaCatalog/optimisticOfflineLock.html) | Проектировать обнаружение конфликтов, когда две вкладки, повторный запрос или устаревший клиент могут изменить одну серверную сущность между чтением и записью. Сверять версию и применять проверку вместе с записью в одной транзакции. | Использовать только при реальном межтранзакционном конфликте. Для атомарной команды Tender с достаточной серверной проверкой отдельное поле версии может быть не нужно. |
| [Test Pyramid](https://martinfowler.com/bliki/TestPyramid.html) | Держать основную матрицу правил и ошибок в быстрых unit/integration/contract-тестах, а небольшое число E2E — для критичных пользовательских путей и взаимодействия слоёв. Ошибку из E2E по возможности воспроизводить на более узкой границе. | Это модель стоимости и уверенности, а не обязательная числовая пропорция. Стабильный высокоуровневый тест сохраняется, если он даёт лучшую практическую защиту. |

## Материалы для условного применения

| Материал | Когда применять | Ограничение |
|---|---|---|
| [Contract Test](https://martinfowler.com/bliki/ContractTest.html) | Когда backend интегрируется с внешним сервисом через test double: проверять, что double сохраняет фактическую форму и поведение внешнего контракта. Для собственных producer/consumer контрактов по-прежнему проверять обе стороны общих Zod-схем. | Статья не доказывает, что каждому внутреннему модулю нужен отдельный consumer-driven-contract инструмент. Проверка production API должна быть безопасной и согласованной с владельцем сервиса. |
| [Feature Toggles](https://martinfowler.com/articles/feature-toggles.html) | Только когда нужно отделить выпуск возможности от развёртывания: определить тип флага, владельца, срок удаления, наблюдаемую конфигурацию и тесты рабочего и fallback-путей. Решение о флаге держать у границы или в composition, не разносить условие по доменной логике. | Feature flag не заменяет сохранённый `Tender Ruleset`: правила активного Tender неизменны. Не добавлять инфраструктуру флагов заранее; временные флаги удалять, долгоживущие считать отдельной продуктовой политикой. |
| [Circuit Breaker](https://martinfowler.com/bliki/CircuitBreaker.html) | Когда повторяющиеся timeout или сетевые ошибки внешнего провайдера способны занять ресурсы backend и вызвать каскадный отказ. Состояние breaker должно наблюдаться, а клиентский fallback — быть явно определён. | Не внедрять по умолчанию для каждого вызова. Сначала нужны timeout, классификация ошибок и доказанный риск повторных отказов; обычные продуктовые ошибки не должны открывать circuit. |

## Материалы, которые не включены

- `Micro Frontends` — проекту пока не нужны независимо развёртываемые frontend
  части, принадлежащие разным автономным командам.
- `How to break a Monolith into Microservices` — у проекта нет подтверждённой
  потребности или операционной готовности к такой декомпозиции.
- `Design Stamina Hypothesis` — полезно объясняет долгосрочную ценность дизайна,
  но не даёт достаточно конкретного решения для текущего инженерного реестра.
- `The Practical Test Pyramid` — содержательно полезен, но для действующих
  правил проекта базовая статья `Test Pyramid` даёт достаточный ориентир без
  дублирования реестра.

## Как добавлять новые материалы

Ссылка добавляется только после полного чтения. Для неё обязательно фиксируются:

1. конкретная проблема проекта, при которой материал следует открыть;
2. применимое правило или способ рассуждения;
3. граница применимости, защищающая от механического внедрения паттерна;
4. дата последней проверки материала.

Если материал лишь помогает найти тему, но не был полностью изучен, он остаётся
поисковым результатом и не включается в этот реестр.
