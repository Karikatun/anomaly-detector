# Локальный benchmark Tender-ботов

## Простой режим: локальный протокол #74/#77

`bun scripts/bot-benchmark.ts --mode simple` выбирает отдельный harness
`simple-bot-benchmark.ts`. Стандартный запуск без `--mode` сохраняет прежние
seed, метрики и пороги ниже. Simple считает три раунда и точность из 12;
сравнивать её с рейтингом standard нельзя.

Новая версия `bot-simple-v1` получает только собственное live-представление и
независимый seed выбора. Она не получает скрытую конфигурацию, её seed или
чужие исследования. Персональную проекцию строит Tender до вызова solver;
проекция лабораторного журнала в simple содержит только записи владельца.
Лёгкий бот выбирает информативные исследования и совместимую полную модель;
сложный выбирает полную допустимую модель с наибольшей ожидаемой точностью
среди оставшихся кандидатов. Контрактных действий нет. Сохранённые standard
`bot-v1`/`bot-v2` не переводятся на новую стратегию. Room назначает версию по
режиму при старте; несовместимая пара режима и версии отклоняется при создании.
Для отката после появления simple-ботов нужен совместимый forward fix:
старый worker не распознаёт новую версию. Удалять матчи для отката нельзя.

Принятый порядок измерения:

1. Сначала первые два открытых pilot до конца и с повтором; затем все 12.
   Seed: `simple-pilot-20261102-0` … `-11`. Первый прогон не является holdout.
2. После проверки pilot сохранить manifest. Он фиксирует хеши исходников
   правил/стратегий/harness, описание режима, разрешённые входы, пороги,
   основную матрицу и восемь резервных seed. Freeze требует полный pilot с
   совпавшим replay на тех же исходниках; существующий manifest не перезаписывается.
3. Holdout использует новые `simple-holdout-20261102-0` … `-7`.
   Для 2/3/4 участников: все easy, все hard, целевой hard с easy-соперниками
   и парный контроль вместо hard; каждый фиксированный участник проходит все
   циклические стартовые места. Это 216 основных и 72 контрольных случая,
   каждый дважды: 576 исполнений, восемь независимых seed-блоков.
4. При отклонении доли побед места более чем на 10 п.п. от `1/n` либо изменении
   вердикта при удалении одного seed добавить **все**
   `simple-reserve-20261102-0` … `-7` с той же матрицей, стратегией и порогами.
   Объединённый отчёт проверяет ровно 16 блоков; выбор удачных seed запрещён.
   Сохраняющийся диагностический сигнал разбирается отдельно и сам по себе
   не является ни статистическим доказательством перекоса, ни автоматическим FAIL.

Целевой участник имеет один и тот же ID и seed выбора в easy/mixed/control;
соперники easy также сохраняют свои ID и seed. Поток выбора закреплён за
участником, а не за местом, и не зависит от world seed. В симуляции один
участник — сценарий человека, остальные — сохранённые серверные боты.
Сценарий получает то же разрешённое представление; истина используется
оценщиком только после complete. PostgreSQL и браузерный worker проверяются
отдельно: in-memory партии не доказывают восстановление или production capacity.

Контроль «накопитель бюджета» выбирает бесплатный слот 4, сохраняет всю
мощность и не использует результаты исследования. Финальная модель —
равномерная допустимая перестановка из 720, выбранная независимым потоком с
rejection sampling без modulo bias. Арифметическое ожидание без информации
равно `6×1/3 + 6×1/2 = 5/12`; проверяется измеренная парная разница, а не
подставленный baseline 5.

Для каждого размера отдельно отчёт агрегирует ротации сначала внутри seed,
затем показывает среднее и 95% CI Стьюдента по блокам. Условия: hard−контроль
≥2 свойства, hard−целевой easy при тех же easy-соперниках ≥0, разрыв средней
точности стартовых мест в однородных easy и hard ≤1 свойства. Все партии
должны завершиться без timeout/invalid commands, а нормализованный журнал и
результат совпасть при повторе. Replay включает команды и квитанции,
разрешённые представления действующего участника до и после каждой команды
и все детерминированные метрики. В отчёт попадает только хеш приватного
журнала, а не сами наблюдения. Реальное время вычисления и `serverTime` в хеш
не входят; версия, игровой порядок и игровые дедлайны сохраняются.
Дополнительно сохраняются время решения, число кандидатов и доказанных
свойств, образцы, лабораторные тесты, сгоревший анализ/резерв, бюджет и
причины tie-break. Повторы и ротации не увеличивают
независимую выборку. Человеческое понимание остаётся `NOT RUN`.

Диагностические счётчики имеют отдельные значения:

- `unavailablePaidSlotChoices` — число слотов 1/2, недоступных по собственному
  бюджету в момент принятого выбора слота; не попытки выполнить запрещённую команду.
- `directPoolUnavailableAtRecon` — собственные ходы разведки, когда в открытом
  пуле нет лично недостающего сигнала; случайный поиск при этом остаётся законным.
- `secondThesisUnaffordable` — ошибочный первый тезис при нулевом бюджете и
  выделенной мощности на два тезиса. Остаток анализа учитывается в сгоревшей мощности.
- `laboratoryInsufficientSamples`/`laboratoryPairsExhausted` — фактически
  пропущенные лабораторные ходы с соответствующей серверной причиной.
- `newDirectedPairs` и покрытие из 30 — уникальные собственные направленные
  пары; `repeatedDirectedPairs` отделяет повтор от числа тестов.
  `informationReducingLaboratoryActions`/`informationReducingTheses` считают
  принятые действия, после которых уменьшилось число совместимых кандидатов.
  Число тестов само по себе не называется пользой исследования.
- `accessByRound` — исходное место участника задаётся отдельно; по каждому
  раунду сохраняются запрошенный и итоговый слот, признак платного слота,
  бюджет и число образцов перед распределением, число образцов после разведки.

Успешный отчёт с `invalidCommands=0` подтверждает отсутствие технических
отклонений команд, но не доступность любой альтернативы. Недоступные
возможности считаются только по перечисленным разрешённым наблюдениям;
запрещённые пробы и oracle скрытой конфигурации не используются.

```sh
bun scripts/bot-benchmark.ts --mode simple --suite pilot --smoke > /tmp/simple-first-two.json
bun scripts/bot-benchmark.ts --mode simple --suite pilot > /tmp/simple-pilot.json
bun scripts/bot-benchmark.ts --mode simple --freeze --pilot-report /tmp/simple-pilot.json --manifest /tmp/simple-frozen.json
bun scripts/bot-benchmark.ts --mode simple --suite holdout --manifest /tmp/simple-frozen.json > /tmp/simple-holdout.json
# Только при принятом диагностическом условии:
bun scripts/bot-benchmark.ts --mode simple --suite reserve --manifest /tmp/simple-frozen.json > /tmp/simple-reserve.json
bun scripts/bot-benchmark.ts --mode simple --suite expanded --manifest /tmp/simple-frozen.json --combine /tmp/simple-holdout.json /tmp/simple-reserve.json > /tmp/simple-expanded.json
```

Неполная/повторяющаяся матрица отклоняется. Для первоначального holdout
`summary.accepted=false` и exit 1 также обозначают необходимость расширения;
нужно читать отдельные численные gates и диагностические поля.
`diagnosticUnresolved` в расширенном отчёте оставляет `status=NEEDS_ANALYSIS`
и `accepted=false`, даже при `numericAccepted=true`: это ожидание разбора
причин, а не автоматический численный FAIL. Итоговый вывод требует отдельного
разбора сохраняющегося сигнала. Holdout не разрешает
перенастройку политики: настоящий численный FAIL возвращается владельцу.

### Локальные результаты #77 — 2 ноября 2026

Первые два pilot, затем все 12 завершились с совпавшим replay. До первого
holdout был сохранён manifest с независимым pre-holdout review, всеми seed,
порогами и исходниками. Версия политики — `bot-simple-v1`, SHA-256 файла
`simple.ts`: `3370482a435dc5f1e939f9c9d4bcece86453a5a42c57325f59b92de731f739d9`.
Исходники исполнения связаны digest
`cba88230a511a8f583edd69594a83acd88512a0e6213ee54d0f3e11ad8a38ff0`,
файл frozen manifest —
`fc146d56a09a2371676647395d03f13f5dc8c33f535f78777431da53ece8c0eb`.

Основные 288 случаев / 576 исполнений прошли без невалидных команд и
тайм-аутов, replay совпал. По каждому размеру hard−контроль составил +7,5
свойства, hard−easy — 0, разрыв средней точности мест — 0. Однако доля
побед дала заранее определённый сигнал; поэтому добавлены все восемь
резервных блоков с неизменёнными политикой, seed-матрицей и порогами.

Итог расширения — 576 случаев / 1152 исполнений, **16 независимых блоков**.
Все полные журналы команд/квитанций/персональных наблюдений и метрик совпали
при повторе; невалидных команд и тайм-аутов — 0. На первом исполнении каждого
случая принято суммарно 28 816 команд. Максимум выбора команды на этой
машине — 7,234 мс; это локальное наблюдение, не production capacity.

| Участников | hard−контроль, свойства из 12 | 95% CI по 16 блокам | hard−easy | Разрыв точности мест easy/hard |
| --- | ---: | --- | ---: | ---: |
| 2 | +6,875 | [5,694; 8,056] | 0 | 0 / 0 |
| 3 | +6,875 | [5,694; 8,056] | 0 | 0 / 0 |
| 4 | +6,875 | [5,694; 8,056] | 0 | 0 / 0 |

Обе сложности во всех исследовательских случаях достигли потолка 12/12 и
одного оставшегося кандидата до сдачи. Выполнено условие «hard не хуже easy»;
более сильная игра hard этим набором не установлена. Средние и ротации не
доказывают понимание человека или универсальное равенство стартовых мест.

Диагностика побед сохранилась на расширении, одинаково для easy и hard:

| Участников | Доли побед исходных мест 1…n |
| --- | --- |
| 2 | 100%; 0% |
| 3 | 62,5%; 20,833%; 16,667% |
| 4 | 76,563%; 0%; 23,438%; 0% |

По всем 576 случаям победу определили точность в 32, бюджет в 329 и серверный
порядок сдачи в 215 случаях. Исключение одного блока не меняло численные
вердикты. Машинный результат остаётся **`NEEDS_ANALYSIS`, `accepted=false`**
при `numericAccepted=true`; общий баланс PASS не заявляется. Последующее
решение владельца от 2 ноября 2026: оставить текущее распределение мощности,
экономику и правила, а баланс простого режима пересмотреть позже в #74.
Функциональное завершение #77 продолжается по проверкам законности bot/mixed
пути, приватности, восстановления и совместимости standard. Предложенные
альтернативы не приняты; стратегия после holdout не перенастраивается.
Исходные численные критерии и диагностический итог сохраняются, #74 остаётся
открытым. Это заменяет прежний порядок «сначала пересмотреть баланс до
завершения #77» и не означает баланс PASS или принятие нового набора правил.

Причины видны в фактической траектории. Однородные боты всегда просят слот 6,
достигают одинаковых 12/12, а три раунда не выравнивают бюджетные компенсации
для двух и четырёх мест. В двухместных однородных партиях средний остаток
бюджета — 6,25 против 5,25; в четырёхместных — 6,344 / 5,281 / 6,281 / 5,281.
Для трёх мест средний бюджет одинаков — 6,25, но индивидуальные расходы и
порядок сдачи всё ещё влияют на победу. Harness и текущий bot runner обходят
исходные места последовательно и принимают одну команду за проход; при равной
точности и бюджете более ранняя сдача даёт преимущество. Сценарий человека
стоит в той же очереди; реальное человеческое время решения не измерялось.
Сигнал не отбрасывается из-за этого ограничения модели.

Есть и ограничение политики: выбор информационного тезиса при единственном
кандидате всё ещё разрешает произвольную гипотезу с нулевой новой информацией;
ненужная ошибка может увеличить расход бюджета. Политика после чтения holdout
не перенастраивалась. Изменённую стратегию нужно проверять через открытый pilot
и новый заранее зафиксированный, ещё не просмотренный holdout; эти 16 блоков
уже являются историческим набором воспроизведения.

**Исправление расчёта неопределённости.** После прогона обнаружено, что общий
helper для 16 блоков использовал fallback 1,96 вместо `t(15)=2,131` из
[таблицы NIST](https://itl.nist.gov/div898/handbook/eda/section3/eda3672.htm).
Это исправлено отдельной строкой таблицы и проверкой известного интервала
для 16 значений. Из неизменённых raw results построен новый
`expanded-ci-corrected.json`: CI расширился до [5,694; 8,056], среднее,
численные gates и `NEEDS_ANALYSIS` не изменились. В simple нет порога CI.
Исходные frozen/main/reserve/expanded файлы и replay-хеши сохранены; новые
исполнения не запускались. Коррекция явно содержит версию и SHA нового
оценщика; она не выдаётся за исполнение на неизменившемся полном исходнике.
Локальные файлы результатов находятся вне репозитория в
`/private/tmp/codex-mode77-core-evidence/`; приватные наблюдения в них заменены
хешем. Человеческая проверка остаётся `NOT RUN`.

`scripts/bot-benchmark.ts` запускает детерминированные партии Tender в памяти. Он не создаёт записей PostgreSQL, не обращается к сети и не использует скрытую конфигурацию при выборе команды: человек в симуляции действует через `bot-v1`, бот — через `bot-v2` с заданной сложностью.

Каждый случай воспроизводится второй раз. Скрипт сравнивает нормализованный журнал команд и итоговые очки; различие останавливает прогон. Метрики решения измеряются вокруг `chooseBotCommand`; CPU и RSS измеряются процессом Bun на локальной машине. Каждый отчёт содержит `environment`: версию Bun, платформу, архитектуру, модель CPU и объём системной памяти.

## Наборы

`baseline` использует 12 открытых seed `bots-baseline-20260907-0` … `-11`. Это диагностический набор: он печатает метрики, но не выносит quality verdict.

`holdout` использует 8 зафиксированных seed `bots-holdout-20260907-0` … `-7`. Набор проходит шесть составов лобби, три варианта сложности (`easy`, `hard`, `mixed`) и циклические сдвиги порядка мест каждого состава. Это не перебор всех факториальных перестановок. В нём 480 случаев. Сравнение hard/easy агрегируется сначала внутри seed, затем строится 95% доверительный интервал Стьюдента: для восьми seed `t(7)=2.365`.

## Запуск

Во всех командах нужен Bun в `PATH`:

```sh
PATH="/opt/homebrew/bin:$HOME/.bun/bin:$PATH" bun scripts/bot-benchmark.ts --suite baseline > /tmp/bots-baseline.json
PATH="/opt/homebrew/bin:$HOME/.bun/bin:$PATH" bun scripts/bot-benchmark.ts --suite holdout > /tmp/bots-holdout.json
```

`--smoke` запускает два представительных случая. Это проверка пути запуска, а не quality verdict; при отсутствии пар CI содержит `mean`, `lower` и `upper` со значением `null`.

```sh
PATH="/opt/homebrew/bin:$HOME/.bun/bin:$PATH" bun scripts/bot-benchmark.ts --suite holdout --smoke
```

Если длительный процесс должен быть разбит на короткие локальные запуски, запускайте каждый frozen seed отдельно, а затем объедините отчёты. Объединение проверяет отсутствие дубликатов и точное соответствие всей frozen-матрице из 480 случаев; оно возвращает ненулевой код, если quality gate не пройден.

```sh
for index in {0..7}; do
  PATH="/opt/homebrew/bin:$HOME/.bun/bin:$PATH" \
    bun scripts/bot-benchmark.ts --suite holdout --seed-index "$index" \
    > "/tmp/bots-holdout-$index.json"
done
PATH="/opt/homebrew/bin:$HOME/.bun/bin:$PATH" \
  bun scripts/bot-benchmark.ts --combine-holdout /tmp/bots-holdout-{0..7}.json \
  > /tmp/bots-holdout.json
```

## Утверждённый quality gate holdout

| Проверка | Порог |
| --- | ---: |
| Завершение случаев | 100% |
| Precision consensus свойств и направленных взаимодействий | 100% |
| Coverage свойств easy | ≥ 95% |
| Среднее преимущество hard над easy | ≥ 5 очков |
| Нижняя граница 95% CI преимущества hard | > 0 |
| Pooled p95 выбора команды каждого уровня | ≤ 10 мс |
| Наблюдаемый RSS на этой машине | ≤ 512 MiB |

Полный `holdout` и `--combine-holdout` включают в JSON объект `qualityGate` с порогами, отдельными проверками и `accepted`. При любой неуспешной проверке процесс завершится с ненулевым кодом. `baseline` и smoke намеренно не формируют утверждений о качестве.

## Зафиксированные локальные результаты 2026-09-07

Baseline — диагностический: 720 случаев, 63 156 команд, совпали все повторные хеши. Easy: средний рейтинг `24.0749`, pooled p95 `0.546334 ms`, максимум `10.652042 ms`; hard: `31.7138`, `0.1275 ms`, `1.26975 ms`. Максимальный RSS процесса — `377,569,280` bytes, максимальный CPU на случай — `160,300 µs`. Эти числа не являются quality verdict.

Holdout прошёл: 480/480 случаев, без timeout; consensus свойств и взаимодействий — 100%, coverage easy — 100%. Средняя разница hard–easy составила `+7.76146` очка, 95% CI `[+7.18018, +8.34273]`. Pooled p95: easy `0.61075 ms`, hard `0.143125 ms`; максимальный RSS `296,091,648` bytes. Средние очки: easy `24.2119` (472 bot-runs), hard `31.8234` (368 bot-runs).

RSS shard-прогона измеряется в отдельном короткоживущем процессе и поэтому не заменяет RSS длительного worker-процесса; для утверждённого локального порога используется наблюдённый RSS отчёта конкретного прогона. Это локальное воспроизводимое измерение на фиксированных seed, а не доказательство оптимальности стратегии или универсальной производительности. CPU, RSS и задержки зависят от машины, прогрева и фоновой нагрузки. Human acceptance для этой функции остаётся pending.

## Временная остановка создания ботов

`ROOM_BOT_CREATION_DISABLED="true"` временно запрещает добавлять новых ботов в ожидающие комнаты. Уже добавленных ботов можно удалить или изменить им сложность, а полные комнаты можно запустить. Матчи, которые уже начались, и серверный worker продолжают работать. По умолчанию флаг выключен.

После изменения `ROOM_BOT_CREATION_DISABLED` требуется штатно перезапустить API
с новым окружением; worker останавливать не нужно. Для возврата добавления ботов
установите `false` и перезапустите API. Это запрещает новые добавления, но не
откатывает сохранённые составы комнат. Миграция
`20260907171459_add_room_bots` должна быть применена перед запуском нового backend;
её откат с потерей участников не используется как способ выключения функции.
При раздельном обновлении API, worker и webapp запретите новые добавления до
обновления всех трёх частей. Существующие стратегии `bot-v1` и `bot-v2` должны
оставаться исполняемыми для сохранённых матчей.

## Ограниченный замер PostgreSQL worker

`bun scripts/bot-worker-benchmark.ts` требует `TEST_DATABASE_URL` на отдельную
базу `*_test` с применёнными миграциями и без активных Tender. Скрипт создаёт
50 матчей по три бота, выполняет начальный выбор слотов реальным обработчиком
и удаляет только собственные записи. Перед запуском примените миграции обычной
командой `bun run --cwd backend prisma:deploy` с `DATABASE_URL` этой тестовой базы.

На Apple M4 Max, darwin arm64, Bun 1.3.14: 150 уникальных команд без пропусков
и повторов; 1 477 мс работы, 1 068 271 мкс CPU, наблюдаемый RSS 254 525 440 B,
p95 длительности порции 256.36 мс. Мягкий бюджет 250 мс допускает завершение
начатой транзакции. Стенд запускает порции без паузы и проверяет начальные ходы;
это не измерение пропускной способности production или нагрузки полного матча.
В обычном worker между проходами действует период 500 мс. API добавления ботов
использует существующий бюджет авторизованных изменений; вместимость комнаты
остаётся не более четырёх участников и не менее одного человека.

## Ручная приёмка

Автоматические тесты не заменяют игры людей. До окончательного принятия #55
нужно записать реальные устройства и версии браузеров, пройти полные партии
с лёгким и сложным ботами и отдельно отметить замечания к понятности правил,
темпу, балансу и интерфейсу. Пока эти сведения отсутствуют, ручная часть #55
остаётся открытой. Production-публикация в эту задачу не входит.
