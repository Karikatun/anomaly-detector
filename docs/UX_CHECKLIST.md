# UX Checklist

Этот чек-лист — рабочий критерий приёмки для изменений пользовательского
интерфейса Anomaly Detector. Он дополняет визуальный контракт в
[DESIGN_SYSTEM.md](DESIGN_SYSTEM.md), правила игры в
[GAME_DESIGN_BRIEF.md](GAME_DESIGN_BRIEF.md) и распределение автоматизированных
проверок в [TESTING.md](TESTING.md).

Не нужно механически проходить весь документ после локальной косметической
правки. Для изменяемого flow выбираются применимые пункты, а для нового или
поведенчески значимого flow заполняется вся матрица состояний.

## Быстрый UI QA

Полный прогон выполняется для существенного UI/UX-изменения на `1440×900`,
`1024×768` и `390×844`. Для узкого `Direct`-исправления выбираются только
затронутые композиции и пункты: desktop/mobile обязательны, когда риск может
различаться между ними; промежуточный viewport нужен при layout, overflow или
height-sensitive изменении. Узкая semantic accessibility-правка остаётся
`TDD-first` по `AGENTS.md`, но без изменения композиции проверяется на
затронутом viewport через accessibility tree, keyboard/focus и rendered result,
а не через ритуальный прогон всех размеров.

- [ ] Сразу видны этап, таймер, ключевой ресурс, текущий выбор и один primary CTA.
- [ ] Родственные блоки выровнены, используют общий spacing rhythm и не прыгают
  при изменении данных.
- [ ] Нет overflow, случайного горизонтального скролла, обрезанного текста и
  перекрытия sticky-элементами.
- [ ] Важные сведения и действия доступны без hover; клавиатурный фокус виден.
- [ ] Rapid clicks, min/max, deselection и повторная отправка не создают
  неверное состояние.
- [ ] Disabled-состояние объясняет ограничение, а ошибка находится рядом с
  причиной, говорит, как её исправить, и не сдвигает layout.
- [ ] Loading и асинхронный результат резервируют место; server-accepted state
  визуально отличается от локального выбора.
- [ ] Экран просмотрен с реальными заполненными данными, а не только в empty
  state; исправлены замеченные проблемы до завершения задачи.

### Минимальная state matrix экрана

Неприменимые строки помечаются `N/A`. Для сложного flow используется полная
матрица ниже.

| State | Что должно быть видно | Что проверить |
|---|---|---|
| Loading / Empty | Что ожидается или почему данных нет; следующий шаг | Зарезервировано место, доступные действия безопасны |
| Ready | Доступные варианты, ограничения, ресурс и CTA | Первый выбор, клавиатура, touch, rapid clicks |
| Selected / Local draft | Что выбрано, эффект, стоимость и остаток | Deselect, замена, min/max, невозможный дубль |
| Disabled | Причина недоступности и условие восстановления | Контрол нельзя активировать мышью или клавиатурой |
| Validation / Server error | Конкретная причина и способ исправления | Ошибка рядом с причиной, работа не потеряна, layout стабилен |
| Submitting | Отправляемый выбор и занятость действия | Повтор заблокирован, UI не прыгает |
| Accepted / Waiting | Что принял сервер и что происходит дальше | Отличается от draft, дальнейшее действие однозначно |
| Recovered / Completed | Актуальное состояние после сбоя или финала | Нет устаревших CTA и ложной редактируемости |

### Удаление дублирующей информации

Один факт должен иметь одно основное место отображения. Повтор нужно удалить,
если одновременно выполняются условия:

- он сообщает тот же факт теми же словами или числом;
- основной источник виден в момент принятия решения;
- повтор не добавляет действие, новый статус, последствие или способ исправить
  ошибку;
- после удаления игрок по-прежнему понимает выбор, ограничение и следующий шаг.

Повтор допустим только когда он предотвращает ошибку: подтверждает точную цену
или необратимое последствие, сохраняет критический ресурс или статус видимым
после прокрутки, либо различает локальный выбор и серверно принятый результат.
Desktop- и mobile-композиции могут размещать один факт по-разному, но не должны
показывать его дважды в одном контексте без такой причины.

## Краткая запись в задаче

Перед реализацией зафиксировать:

- цель игрока;
- основной успешный сценарий;
- необратимые действия и расходуемые ресурсы;
- источник истины и момент, когда действие считается принятым;
- применимые ошибки, дедлайн и восстановление;
- затронутые приватные и публичные данные;
- desktop- и mobile-представление;
- основной пользовательский сигнал готовности.

### Формальный CUJ и evidence-матрица

Формальный critical user journey с устойчивыми `UXC-*`/`UXF-*` ID нужен только
для нового или существенно перепроектированного критического flow: доступа или
восстановления аккаунта, privacy/consent, необратимого игрового решения либо
другого пути, где ошибка заметно меняет доступ, данные или результат игрока.
Зафиксировать роль и цель, предусловия, начальный route, шаги, наблюдаемый итог,
применимые состояния и точки evidence; затем связать каждый критерий с
`PASS/FAIL/N/A/BLOCKED` и воспроизводимым доказательством.

Для локального исправления или развития существующего flow формальная матрица
не нужна: достаточно краткой записи выше, применимых состояний и фактически
пройденного rendered evidence. ID не создаются ради отчётности.

## Информационная иерархия

- [ ] Без чтения справки понятно, какая сейчас фаза и чей ход.
- [ ] Таймер и состояние соединения видны в момент принятия решения.
- [ ] На экране один доминирующий следующий шаг.
- [ ] Основное действие расположено раньше вспомогательной истории и справки.
- [ ] Заголовки точно описывают содержимое раскрываемых секций.
- [ ] Важная информация не спрятана только в tooltip, цвете или hover.
- [ ] Длинные списки имеют понятный порядок; фильтрация или виртуализация
  добавляются только при подтверждённой потребности.

## Выбор и подтверждение

- [ ] Игрок может проверить выбор до отправки.
- [ ] Переключение режима не подтверждает и не очищает выбор автоматически.
- [ ] Необратимое действие явно описывает последствие и расход ресурсов.
- [ ] Текст CTA называет действие и объект, а не использует общее «ОК».
- [ ] Повторная отправка блокируется, пока исход предыдущей не определён.
- [ ] После успеха показано, что именно принял сервер.
- [ ] Отмена или закрытие не создаёт скрытый побочный эффект.

## Матрица состояний

Для каждого применимого состояния проверить текст, доступные действия и путь
перехода дальше.

| Состояние | Проверка |
|---|---|
| Loading | Понятно, какие данные или действие ожидаются; интерфейс не выглядит сломанным |
| Empty | Объяснена причина отсутствия данных и следующий возможный шаг |
| Ready | Доступно только валидное действие; выбор можно пересмотреть |
| Local draft | Ясно, что изменение ещё не сохранено сервером |
| Saved draft | Ясно, что черновик сохранён, но окончательно не отправлен |
| Submitting | Повтор заблокирован, выбранные данные остаются видимы |
| Accepted | Есть серверно подтверждённая сводка принятого действия |
| Waiting | Понятно, кого или что ожидаем и что уже принято у текущего игрока |
| Disabled | Объяснено, почему действие недоступно и изменится ли это состояние |
| Validation error | Ошибка связана с полем/выбором и исправима без потери работы |
| Conflict | Получено актуальное состояние и сказано, нужно ли повторять действие |
| Deadline | Показано серверное последствие тайм-аута и новая доступная фаза |
| Reconnecting | Рискованные действия заблокированы, причина видна |
| Recovered | Различимы сохранённое, отправленное и ещё редактируемое состояние |
| Completed | Нет ложного впечатления, что результат можно изменить |

## Приватность и соревновательная честность

- [ ] Клиент получает только разрешённые текущему игроку приватные данные.
- [ ] «Видят все» и «Только вы» обозначены текстом, а не только цветом.
- [ ] Ожидание, список игроков и публичный журнал не раскрывают чужой выбор,
  стратегию, тезисы, образцы или приватные измерения.
- [ ] Skeleton, optimistic UI и error-текст не позволяют вывести скрытое
  состояние.
- [ ] После завершения приватные данные раскрываются только в разрешённом
  участникам аудите.

## Responsive и доступность

- [ ] Flow проверен минимум на desktop и mobile portrait.
- [ ] Основной CTA, таймер и критический статус не требуют горизонтального
  скролла.
- [ ] На мобильном меняется композиция и приоритет информации, а не только
  уменьшается текст.
- [ ] Области нажатия соответствуют WCAG 2.2 AA: не меньше `24×24 CSS px` либо
  имеют допустимый интервал до соседних целей. Для частых, последовательных или
  трудно отменяемых действий отдельно оценивается увеличенная область вплоть
  до ориентира `44×44 CSS px` из enhanced-критерия AAA; это не универсальная
  обязательная высота каждого контрола.
- [ ] Для полей выбраны соответствующие назначению `type`, `inputmode` и
  `autocomplete`; мобильная клавиатура проверена на реальном вводе. `inputmode`
  считается только подсказкой клавиатуре и не заменяет schema/server validation.
- [ ] Каждое изображение оценено в контексте экрана: информативное получает
  краткий осмысленный `alt`, а декоративное или полностью повторяющее соседний
  текст — `alt=""`. Иконка внутри именованной кнопки не дублирует её label.
- [ ] Интерфейс доступен с клавиатуры, а фокус имеет видимое состояние.
- [ ] Диалог удерживает фокус и возвращает его на открывший элемент.
- [ ] Tooltip доступен через фокус или нажатие и не перекрывает цель.
- [ ] Статусы и результаты различимы без цвета.
- [ ] Динамический статус объявляется вспомогательным технологиям без лишнего
  повторения.

## Текст и терминология

- [ ] Используются термины из [CONTEXT.md](../CONTEXT.md) и
  [RULES_REFERENCE.md](RULES_REFERENCE.md).
- [ ] Пользовательские строки находятся в доменном i18n-чанке.
- [ ] Ошибка объясняет следующий полезный шаг, а не только техническую причину.
- [ ] Loading-текст описывает реальное действие.
- [ ] Публичность, необратимость и серверное подтверждение сформулированы
  буквально, без двусмысленности.

## Проверка и доказательства

- [ ] Выбран самый высокий практичный уровень автоматизированной проверки по
  [TESTING.md](TESTING.md).
- [ ] Критический cross-layer flow защищён E2E, если сценарий стабилен и
  поддерживаем.
- [ ] Матрицы правил, конфликтов и ошибок проверены unit/integration-тестами, а
  не раздувают E2E.
- [ ] Косметические изменения проверены просмотром или скриншотами, а не
  утверждениями о CSS-классах.
- [ ] Для соревновательного flow использованы изолированные игроки без доступа к
  чужому приватному состоянию.
- [ ] Основной пользовательский сигнал действительно проверен, а не заменён
  одним typecheck или lint.

## Работа с внешними референсами

- [ ] Сформулирована задача до поиска референсов.
- [ ] Для нового или существенно изменяемого интерфейса вопросы из
  [KeepSimple UX Core Guide](https://keepsimple.io/uxcg) использованы для поиска
  гипотез о заметности, ошибках, обратной связи и упрощении; ответы проверены на
  сценариях проекта, а не приняты как готовые правила.
- [ ] Сравниваются несколько реальных flows, а не копируется один экран.
- [ ] Из референса выписано поведение и состояния, а не только стиль.
- [ ] Решение собрано из существующих токенов и примитивов проекта.
- [ ] Сгенерированный `DESIGN.md`, taste-map или image-to-code-результат не
  создаёт второй визуальный контракт рядом с `DESIGN_SYSTEM.md`.
- [ ] Сторонний skill просмотрен до использования: понятны его инструкции,
  скрипты, сетевые обращения и требуемые права.
- [ ] Переносимый компонент проверен по лицензии, зависимостям, доступности,
  responsive-состояниям и соответствию терминологии проекта.
- [ ] Новая зависимость не добавляется без отдельного продуктового и
  инженерного обоснования.
- [ ] Статический AI-аудит дополнен проверкой фактического flow; скриншот,
  accessibility snapshot или зелёный E2E не используются как единственное
  доказательство качества.
- [ ] Когнитивная гипотеза проверяется на игроках и не превращается в dark
  pattern.

Актуальные нормативные источники и исследовательские инструменты, их роль и дата
просмотра перечислены в разделе «Источники и референсы» документа
[DESIGN_SYSTEM.md](DESIGN_SYSTEM.md). Исследовательские инструменты помогают
формировать гипотезы, но не заменяют правила этого чек-листа и первичные
стандарты доступности.
