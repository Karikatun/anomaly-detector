# Аналитика лендинга и объявлений

Решение от 10 сентября 2026 года: считать просмотры лендинга и нажатия
«Пройти обучение» без идентификаторов посетителей и панели согласия.
Регистрация, завершение обучения и подтверждение почты в этот сбор не входят.
Счётчики появляются в операторском разделе «Аналитика» за 7, 30 или 90 дней.

## Что означают числа

- Просмотр — загрузка страницы, при которой браузер отправил событие, а API
  принял его. Повторная загрузка увеличивает счётчик.
- Переход — первое нажатие на CTA в пределах загруженной страницы. Это не
  доказательство успешной регистрации или даже загрузки следующей страницы.
- Доля переходов — число нажатий, делённое на число просмотров. Это не конверсия
  уникальных людей. Блокировщик, сеть и закрытие вкладки могут терять события;
  повторная отправка может увеличивать счётчик. Значение может превышать 100%.
- Известные роботы учитываются отдельно и исключены из основных чисел.
  Классификация по User-Agent не доказывает, что остальной трафик — люди.
- Отчёт не равен платным кликам Директа: расходы и клики рекламной площадки
  остаются в её кабинете. Неизвестные метки не создают новые строки объявлений.

## Данные и границы

Браузер отправляет только `event`, разрешённый `campaign` и hostname источника.
Сервер сразу сводит источник к категории и увеличивает дневные счётчики:
дата, вид события, категория источника или ключ объявления, класс трафика,
количество. Полный URL, `yclid`, `utm_source`, `utm_medium`, IP, cookie, account ID,
journey ID и сырые события в аналитические таблицы не попадают. Аналитический
клиент не использует cookie или localStorage; запросы идут с `credentials: omit`.

Разрешены только `landing_view` и `tutorial_cta`. Маршруты согласия и связанного
пути в режиме `aggregate` отсутствуют. Старый режим `consented` остаётся в коде,
но этот релиз его не включает. Старые метрики пути не смешиваются с новыми.
Защита API использует отдельный краткоживущий HMAC IP в существующем контуре
лимитов: до 120 запросов в минуту с адреса. Он не связывается с аналитическими
счётчиками и не включается в операторский отчёт. Проверка Origin ограничивает
браузерные источники, но не удостоверяет рекламные клики внешних клиентов.

Агрегаты хранятся 13 месяцев; `maintenance:cleanup` ежедневно удаляет просроченные
строки, включая новую таблицу объявлений. При штатной работе задержка удаления
после срока — не более 24 часов. Ключи объявлений нужно сохранять в allowlist,
пока нужен их отчёт: удалённый ключ скрывается, сохранённые строки доживают
срок хранения. Метки не переиспользуют для других объявлений.

## Конфигурация выпуска

API и worker используют один проверенный backend image. В окружении API:

```dotenv
ANALYTICS_ENABLED=true
ANALYTICS_MODE=aggregate
ANALYTICS_ORIGINS=https://anomaly-detector.ru,https://app.anomaly-detector.ru
ANALYTICS_CAMPAIGN_ALLOWLIST=ad_01,ad_02,ad_03,ad_04,ad_05,ad_06
```

Сборка лендинга из каталога `website`:

```bash
PUBLIC_WEBSITE_URL=https://anomaly-detector.ru \
PUBLIC_WEBAPP_URL=https://app.anomaly-detector.ru \
PUBLIC_ANALYTICS_API_URL=https://api.anomaly-detector.ru \
PUBLIC_ANALYTICS_MODE=aggregate \
PUBLIC_ANALYTICS_CAMPAIGN_ALLOWLIST=ad_01,ad_02,ad_03,ad_04,ad_05,ad_06 \
bun run build:release:analytics
```

Обычный `build:release` сохраняет запрет случайного включения аналитики.
Игровой клиент собирается обычным release-профилем без `VITE_ANALYTICS_ENABLED`,
с утверждёнными legal values и полным SHA релиза из runbook. Операторский клиент
тоже пересобирается: новый контракт добавляет режим и строки объявлений.
Новый adminapp читает старый ответ API, поэтому его можно опубликовать первым;
старый строгий клиент не читает новый ответ.

Порядок: точный SHA и зелёный CI → резервная копия → аддитивная миграция
`20260910095243_add_analytics_campaign_aggregates` → новый adminapp → API и worker
из одного image → лендинг и legal-страницы игрового клиента. Перед публикацией
сверить фактическую карту данных с privacy policy и подтвердить работающую
ежедневную очистку. Общие owner/provider/legal gates в #2 и #31 не объявляются
закрытыми этим техническим срезом.

После публикации проверить в браузере обе записи по одной метке, отсутствие
панели и аналитических cookies, продолжение CTA при заблокированном сборщике,
404 связанных маршрутов, запрет публичному origin обращаться к auth/operator
API, доступность отчёта только оператору и успешный запуск cleanup. Эти live
проверки обязательны до утверждения, что сбор работает в production.

Отключение: `ANALYTICS_ENABLED=false` и обычная сборка лендинга без аналитических
переменных. Миграция только добавляет таблицу; удалять её при откате не нужно.
Откат API и adminapp согласованный, к непосредственно предшествующему проверенному
релизу. Старый worker не очищает новую таблицу: при откате сохранить новый
совместимый cleanup либо восстановить его до наступления срока удаления.
